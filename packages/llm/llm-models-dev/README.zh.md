# @deepseek-ai/dsh-llm-models-dev

[English](README.md) | 中文

## 概述

挂载 `@deepseek-ai/dsh-llm-models-dev`，可在组合内提供 models.dev 模型目录服务。该服务按计划抓取公开的目录文档，把最近一份留在磁盘上，并发布每个提供方的模型及其上下文窗口、输出上限、输入类型与思考级别。`dsh-llm-pi-ai` 读取它，因此提供方路由的模型列表无需手写 profile 即可跟随提供方的新版本发布。该目录描述的是能力，而非线上协议方言：同时被已装 pi-ai 目录描述的模型保留该条目的协议知识。

<a id="use-this-package"></a>
## 使用本包

当组合中的提供方路由应从实时目录而非已装包所附的 pi-ai 目录副本取得模型列表时，挂载本插件。本插件是目录服务：它拥有抓取、计划与解析后的事实。由哪个适配器提供方路由由路由自己决定，也就是 `dsh-llm-pi-ai` 的职责。

### 何时选择

当提供方发布模型的速度快于打包依赖能列出的速度时选择它：新的旗舰模型、改名的预览版、仅编码套餐才开放的模型。当已装目录已列出路由服务的每个模型时跳过它；当部署方不允许运行时访问公网时也跳过它。

### 最小配置

```yaml
- id: llm-models-dev
  name: '@deepseek-ai/dsh-llm-models-dev'

- id: llm-pi-ai
  name: '@deepseek-ai/dsh-llm-pi-ai'
  config:
    providers:
      minimax-cn:
        apiKeyEnv: MINIMAX_CN_API_KEY
```

| 字段 | 默认值 | 含义 |
|---|---|---|
| `url` | `https://models.dev/api.json` | 目录端点 |
| `refreshIntervalMs` | `21600000` | 重新抓取目录的间隔（毫秒） |
| `timeoutMs` | `30000` | 单次目录请求的最长耗时（毫秒） |
| `maxBytes` | `16777216` | 接受的最大目录回复字节数 |
| `includeDeprecated` | `false` | 目录是否保留 models.dev 标记为已弃用的模型 |
| `cachePath` | `~/.dsh/cache/models-dev.json` | 抓取到的目录留存在何处，供下次启动使用 |
| `retryIntervalMs` | `30000` | 失败的一次尝试在下次尝试前等待多久（毫秒） |
| `dshHome` | `$DSH_HOME` 或 `~/.dsh` | 解析默认缓存位置所依据的 harness home |

### 路由提供什么

路由的键就是目录记录该提供方所用的提供方 id，因此名为 `minimax-cn` 的路由会取用 models.dev 为 `minimax-cn` 列出的模型。目录决定路由服务哪些模型、每个模型能做什么；已装 pi-ai 目录仍决定如何与它描述的模型对话，因此两个目录都列出的模型保留 pi-ai 的协议、兼容开关与输入限制。只有目录列出的模型取用该提供方 AI SDK 包所说的线上协议，以及目录公布的端点。

路由的 `models` 列表仍然整体替换目录，`modelOverrides` 仍然只重塑其中一个模型，因此必须服务精确集合的部署方在自己的 profile 里写明。

### 配置界面能得到什么

目录记录的每个提供方都是配置界面可以提供的路由，因此 Models 页面会把它与已装目录提供的提供方并列列出。所提供的条目给出路由键、该提供方服务的端点、其模型使用的线上协议以及其凭据读取的环境变量；路由的模型与容量在路由配置好之后来自目录。其 AI SDK 包所指协议本构建无法构造的提供方不会被提供——路由仍可手写声明并自带协议——目录未记录任何 chat 模型的提供方同样不会被提供，因为那类路由无模型可服务。

所列清单与背后的目录一样新：有目录的组合立即给出目录中的提供方，从未抓取过目录的组合在首份文档到达前只给出已装目录的提供方。配置界面可以请服务再次抓取目录；抓取会替换当前目录、更新缓存，并像其他替换一样公布，因此投射出的提供方清单会跟随它。

### 失败与恢复

抓取失败会保留上一份目录，在 `retryIntervalMs` 之后重试，并且不会让组合停止服务；服务记录该失败并让组合继续服务。目录未以可用形式携带的记录会被跳过并计数，因此一条损坏的条目不会让部署方失去其他所有提供方的模型。无法被满足的配置——相对端点、非正间隔——在插件挂载时失败。

<a id="understand-the-implementation"></a>
## 理解实现

<details>
<summary>实现内部细节——点击展开</summary>

本节解释目录服务背后的设计；可观察行为已完整覆盖在[使用本包](#use-this-package)中。

### 设计理念

服务拥有一份目录以及保持它最新的计划，消费方按身份读取它：刷新后的目录是一个新对象，因此按该身份做记忆的消费方无需订阅事件即可察觉变化。抓取失败会保留上一份目录，因为一分钟前还当前的目录好过没有目录。

该目录描述能力，而非方言。模型*是什么*——它的上下文窗口、输出上限、输入类型、思考级别——来自 models.dev。如何与它*对话*来自已装的 pi-ai 目录。models.dev 把线上协议放在能力清单无法承载的唯一位置：实现该提供方的 AI SDK 提供方包，而那个包只说一种协议。

### 源码地图

| 文件 | 职责 |
|---|---|
| [`src/index.ts`](src/index.ts) | 服务：配置、抓取计划与发布的快照 |
| [`src/client.ts`](src/client.ts) | 有界的目录抓取与回复读取 |
| [`src/cache.ts`](src/cache.ts) | 留给下次启动使用的磁盘目录 |
| [`src/parse.ts`](src/parse.ts) | 把目录负载读成提供方与模型事实 |
| [`src/types.ts`](src/types.ts) | 消费方读取的事实类型 |

### 读取目录

负载是一份 JSON 文档，每个提供方一条记录、每个模型一条记录。每条记录都由一个只接受 harness 用到的字段、忽略其余字段的窄读取器读取，因此 models.dev 之后新增的字段永远不会让抓取失败。标识字段缺失或损坏的记录会被计为跳过，而不是让整份目录失败。

### 刷新计划

目录保存在磁盘上，因此启动时会先给出它已有的提供方，而网络只决定这些提供方有多新：插件挂载时读取缓存的目录，当它比刷新间隔更旧时才去询问网络。没有缓存的启动会立即抓取一份。抓取成功会写入缓存，因此下次启动就有了；失败的尝试保留上一份目录，并在下一次计划刷新之前很久就重试，因为空目录读起来就是一个缺失的提供方。

回复在字节上限下读取，而不是按其声明的长度读取，因为少报自身大小的服务器不会提前告知读者任何信息。待执行的刷新不会独自让进程保持存活，释放插件会取消正在进行的抓取。被替换的目录以 `llmModelsDev/refresh` 公布，因此把目录投射到配置界面的消费方会重建该投射；该公布不携带载荷，因为当前目录归服务所有，消费方从服务读取它。

</details>

<a id="model-experience"></a>
## 模型体验

### 提供方路由目录

#### 模型看到什么

没有。目录决定路由提供哪些模型，以及每个模型的 `contextWindow`、`maxTokens`、输入模态与思考级别；到达提供方的请求由该路由的适配器组装，模型看到的内容与手写模型列表时完全相同。

#### Token 影响

目录给出模型的 `contextWindow` 与 `maxTokens`，路由据此为请求定量。目录事实不会给请求增加 token，而目录列出但路由未选择的模型永不会被请求。

#### KV Cache 影响

无。目录在组装请求之前被读取，绝不进入提供方负载，因此不会改变请求的前缀或其缓存标识。

## 已知限制与延期工作

<a id="known-limitations-and-deferred-work"></a>

这些限制说明目录服务在哪里停止、由未来工作接续。它们是当前包约束，不是通用模型目录对比或任务积压。

- **该目录是经网络抓取的公开文档**——无法访问 models.dev 的部署方保留上次抓到的目录，从未访问到它的部署方照常服务已装 pi-ai 目录。
- **提供方的身份就是它的 models.dev id**——键不是目录记录的提供方 id 的路由不从它取得任何模型，而是改为服务已装目录。
- **目录陈述能力，而非方言**——只有目录列出的模型没有兼容开关，因此需要兼容开关的端点必须在路由自己的配置里写明。
- **回复被整体读入**——该目录是数兆字节的单份文档，内存中不能容纳它的服务目前还没有流式读取器。
- **缓存的目录整个 harness home 只有一份**——针对不同目录运行多个组合的部署方共用一份缓存，最后一次成功抓取者胜出。
